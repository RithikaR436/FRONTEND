Chapter 07

JavaScript Hoisting, Execution Context & Memory Creation Phase

Hoisting is a compile-time artifact of JavaScript's two-phase Execution Context architecture. In this masterclass, we dissect how the V8 engine scans code during the Memory Creation Phase, analyze why Function Declarations are fully hoisted while Function Expressions fail, and deconstruct classic senior interview puzzles.

7.1 The Two Phases of the JavaScript Execution Context

Whenever JavaScript executes a script or invokes a function, it instantiates an Execution Context consisting of two sequential phases:

Phase 1: Memory Creation Phase (Compile Step)

  • Engine scans the entire scope without executing statements.
  • Allocates memory for all variable and function identifiers.
  • var identifiers are initialized to primitive undefined.
  • function declarations are stored in memory with their complete implementation body.
  • let and const bindings are registered but left uninitialized in the TDZ.

Phase 2: Code Execution Phase (Runtime Step)

  • Engine interprets code line-by-line from top to bottom.
  • Assigns evaluated runtime values into the memory slots allocated in Phase 1.
  • Invokes functions, evaluates math expressions, and manages Call Stack frames.

7.2 Function Declarations vs Function Expressions vs Arrow Functions

The way a function is declared fundamentally determines its hoisting lifecycle: 

// 1. Function Declaration (Fully Hoisted with Body)
invokeSuccess(); // ✅ Output: "Function executed successfully!"

function invokeSuccess() {
  console.log("Function executed successfully!");
}

// 2. Function Expression with var
try {
  invokeVarExpression(); // ❌ TypeError: invokeVarExpression is not a function (It is currently undefined!)
} catch (e) {
  console.error("var expression error:", e.message);
}

var invokeVarExpression = function() {
  console.log("I am a function expression");
};

// 3. Arrow Function with let or const
try {
  invokeArrow(); // ❌ ReferenceError: Cannot access 'invokeArrow' before initialization (Inside TDZ)
} catch (e) {
  console.error("Arrow TDZ error:", e.message);
}

const invokeArrow = () => {
  console.log("I am an arrow function");
};

7.3 Deconstructed Senior Technical Hoisting Puzzles

Puzzle #1: Function Declaration vs Variable Overwriting

var testIdentifier = 100;

function testIdentifier() {
  console.log("I am a function");
}

console.log(typeof testIdentifier); // Output: "number"

// Step-by-step Execution Proof:
// Phase 1 (Memory Creation): Function declaration hoists first -> testIdentifier = [Function]
// Phase 2 (Code Execution): var testIdentifier = 100 overwrites the reference with number 100!

Puzzle #2: Hoisted Local Variable Shadowing Global

var activeCity = "Chennai";

function displayCity() {
  console.log("Local city before assignment:", activeCity); // Output: undefined ⚠️
  var activeCity = "Bangalore";
  console.log("Local city after assignment:", activeCity);   // Output: "Bangalore"
}

displayCity();

// Step-by-step Execution Proof:
// Inside displayCity, local 'var activeCity' hoists to top of function scope as undefined, shadowing global "Chennai"!

7.4 Top 5 Senior Technical Interview Questions & Answers

Q1: Are ES6 Classes hoisted in JavaScript?

Like let and const, ES6 class declarations are hoisted during the Memory Creation Phase, but they remain uninitialized in the Temporal Dead Zone (TDZ). Attempting to instantiate a class via new MyClass() before its declaration statement throws a ReferenceError: Cannot access 'MyClass' before initialization.

Q2: What happens when two function declarations have the exact same name?

During the Memory Creation Phase, the later function declaration completely overwrites the earlier function declaration in memory. When invoked, only the final declared function definition will execute.

Q3: What is the Call Stack and how does it relate to Execution Contexts?

The Call Stack is a LIFO (Last In, First Out) data structure that tracks active execution contexts. The Global Execution Context is pushed first at script start. Whenever a function is invoked, its new Function Execution Context is pushed onto the stack. When the function returns, its frame is popped off the top of the stack.

Q4: Why does calling a var function expression throw a TypeError instead of a ReferenceError?

Because the identifier was hoisted and initialized to undefined during Phase 1. The variable identifier exists in scope (so no ReferenceError), but attempting to invoke undefined() violates the callable contract, triggering TypeError: ... is not a function.

Q5: Does hoisting physically move lines of code to the top of the file?

No. Hoisting is a conceptual mental model. The JavaScript engine never modifies your physical source code; instead, it parses and allocates declarations into memory records during the compile/creation phase before interpreting statements in the execution phase.
