Chapter 01

JavaScript Variables: var, let, const, Memory Lifecycles & TDZ

A deep dive into how variables function under the hood in the JavaScript engine (V8/SpiderMonkey). We explore the memory allocation phases, lexical environment bindings, scope boundaries, the Temporal Dead Zone (TDZ), and architectural differences between legacy and modern declarations.

1.1 The Anatomy & Lifecycle of a JavaScript Variable

In computer science, a variable is an abstraction providing a human-readable identifier (name) bound to a physical storage location in memory. When the JavaScript engine processes any variable declaration, it executes three distinct, sequential phases:

1

1. Declaration Phase

The engine registers the identifier inside the current scope’s Environment Record. The engine is now aware of the variable’s existence in this lexical scope.

2

2. Initialization Phase

Memory space is allocated for the variable binding. In this phase, the variable is initialized with a default placeholder value (e.g., undefined for var).

3

3. Assignment Phase

The runtime engine evaluates the assignment expression and stores the evaluated value directly into the allocated memory slot. 

// Code showing the explicit separation of phases:
let accountBalance;          // [Declaration + Initialization Phase]: Value is undefined in memory
console.log(accountBalance); // Output: undefined

accountBalance = 50000;      // [Assignment Phase]: Storing numeric primitive 50000 into the memory slot
console.log(accountBalance); // Output: 50000

1.3 Behavioral Deep Dive with Executable Examples

1. Scope Leakage Flaw of var

In JavaScript, block statements like if (condition) { ... } do not create a new scope for var. As a result, variables declared inside an if block leak out and pollute the outer scope: 

// Demonstration: var leaks outside curly braces {}
function calculateBonus(isTopPerformer) {
  if (isTopPerformer) {
    var bonus = 10000;
  }
  console.log("Calculated Bonus with var:", bonus); // Output: 10000 (Leaked!)
}
calculateBonus(true);

// With 'let' or 'const', block scope is strictly enforced:
function calculateBonusSecure(isTopPerformer) {
  if (isTopPerformer) {
    let secureBonus = 10000;
  }
  // console.log(secureBonus); // ❌ ReferenceError: secureBonus is not defined
}
calculateBonusSecure(true);

2. const: Binding Immutability vs Object Mutability

const only makes the variable identifier binding immutable. The memory heap contents of an object or array can still be freely modified: 

const serverConfig = {
  host: "127.0.0.1",
  port: 8080
};

// Valid: Modifying internal properties
serverConfig.port = 3000;
serverConfig.timeout = 5000;
console.log("Updated config:", serverConfig);

// Invalid: Reassigning the binding throws a TypeError
try {
  serverConfig = { host: "0.0.0.0" }; // ❌ TypeError: Assignment to constant variable.
} catch (err) {
  console.error(err.name + ": " + err.message);
}

// Truly freezing an object completely:
const frozenConfig = Object.freeze({ apiKey: "SECRET_TOKEN", retries: 3 });
frozenConfig.retries = 10;
console.log("Frozen config retries value:", frozenConfig.retries); // Output: 3 (Unchanged!)

1.4 The Temporal Dead Zone (TDZ) Deep Dive

The Temporal Dead Zone (TDZ) is defined in the ECMAScript specification as the temporal duration between the entrance of a block scope and the execution of the variable's declaration statement:

// Temporal Dead Zone Timeline
1. Scope Entry: Identifier registered in Environment Record without memory initialization.
2. ⏳ TDZ ACTIVE: Any access throws ReferenceError: Cannot access before initialization.
3. Declaration Statement Reached: let token = "OK"; TDZ Ends! 
// Proof: typeof inside TDZ vs undeclared variables
try {
  console.log(typeof undeclaredVar); // Returns "undefined"
} catch (e) {
  console.error("Undeclared:", e.message);
}

try {
  // console.log(typeof declaredWithLet); // ❌ ReferenceError! (TDZ breaks typeof safety)
  let declaredWithLet = "I am ready";
} catch (e) {
  console.error("Inside TDZ:", e.message);
}

1.5 Top 5 Senior Technical Interview Questions & Answers

Q1: Are let and const hoisted in JavaScript?

Yes, absolutely. Both let and const are hoisted to the top of their block scope during the Memory Creation Phase. However, unlike var (which is initialized with undefined), let and const remain in an uninitialized state within the Temporal Dead Zone (TDZ). Accessing them before their declaration line throws a ReferenceError.

Q2: What is the output of declaring const a; without a value?

It throws an immediate compilation error: SyntaxError: Missing initializer in const declaration. const requires an initial value at the moment of declaration because its binding cannot be reassigned later.

Q3: How does let solve the classic asynchronous for loop bug?

With var, a single variable binding is shared across all loop iterations. When asynchronous callbacks run (e.g., setTimeout), they all reference the final mutated value. With let, JavaScript creates a fresh, distinct block-scoped binding for every iteration of the loop, preserving the current index value in each closure.

Q4: What is the difference between Object.freeze() and const?

const applies to the variable identifier binding and prevents variable reassignment, but leaves the object properties mutable. Object.freeze() applies to the object value in memory and makes its direct properties immutable and non-extensible, but does not prevent variable reassignment unless combined with const.

Q5: Does var attach to the global window object in browser environments?

Yes. In global scope, declaring var x = 10; creates a property on the global object (window.x === 10). In contrast, let and const in the global scope are stored in the declarative environment record and never attach to window, preventing accidental global namespace collisions.
